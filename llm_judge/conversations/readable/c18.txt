**client/src/api/admin.js**
```js
export async function exportOrders() {
  const res = await fetch('/admin/orders.csv', { credentials: 'include' });
  if (!res.ok) throw new Error(await res.text());
  return res.blob();
}
```
`credentials: 'include'` tells `fetch` to send cookies along with the request — necessary here because the admin's session/auth cookie is how the server will know who's asking. `.blob()` (instead of `.json()`) tells the browser "don't parse this as text/JSON, give me the raw binary-ish data as a `Blob` object" — the right call since we're receiving a file, not structured data.

**server/routes/admin.js**
Declares `GET /admin/orders.csv` and lists `requireAdmin` as middleware before the controller function. In Express (the framework this repo uses for routing), middleware functions run in a chain, in order, before the final handler — each one can either call `next()` to pass control along or short-circuit by sending a response itself (e.g., a 403). So this line is purely wiring: it says "for this URL and method, run this gate, then this handler."

**server/middleware/requireAdmin.js**
This is the gate itself. It checks something on the request — typically a user object attached earlier by a login/session middleware — to see if that user has admin privileges. If yes, it calls `next()` and the request proceeds to the controller. If no, it ends the request early with a 401/403 status and never lets the controller run. This is the standard way to centralize an authorization check so every admin route doesn't have to repeat the same logic.

**server/controllers/adminController.js**
The orchestrator. It:
1. calls `allForExport()` to get the rows,
2. calls `toCsv(rows, COLUMNS)` to turn them into a CSV string,
3. sets the two response headers,
4. sends the string.

`Content-Type: text/csv` tells the browser what kind of data this is. `Content-Disposition: attachment; filename=orders.csv` is the header that specifically tells the browser "don't display this inline, treat it as a file to download, and suggest this filename" — without it, the browser might just show the CSV as plain text in the tab.

**server/db/orders.js**
Holds `allForExport()`, the actual SQL query function. Keeping queries here rather than in the controller is the repo's convention — it separates "how do I get this data" from "what do I do with it once I have it," so if the export ever needs different columns or filters, this is the one place to change.

Close, but here's the question that should make the gap visible: **when `toCsv(rows, COLUMNS)` runs, which of those two arguments actually decides which fields end up in the output — the shape of the data it's handed, or the list it's told to use?**

One line: `toCsv` only emits whatever's in `COLUMNS`, and `COLUMNS` lives in **server/controllers/adminController.js** — not `server/db/orders.js` — so that's the file you'd edit, even if `allForExport()` still happens to pull `email` from the database.

Here's why that distinction matters. Picture two scenarios:

1. `allForExport()` does `SELECT id, name, email, total FROM orders` — pulling email into memory — but `COLUMNS = ['id', 'name', 'total']` in the controller. The CSV **won't** have email, because `toCsv` only writes out what `COLUMNS` tells it to.
2. `allForExport()` does `SELECT id, name, total FROM orders` — email never even leaves the database — same CSV result.

Both give an identical file. The query controls what data gets *fetched*; `COLUMNS` controls what gets *written*. You could "fix" the leak by narrowing the SQL query (option 2) and that would work too — but if `COLUMNS` still said `email` while the query no longer selected it, you'd get a blank column or a crash, because `toCsv` is iterating `COLUMNS` and trying to pull each field off each row.

So the robust single source of truth for "what's in this CSV" is `COLUMNS` in `adminController.js`. Narrowing the query in `orders.js` is a reasonable *extra* step (avoid fetching data you don't need at all), but it's not what decides the output — `COLUMNS` is.

That's exactly the distinction you spotted and called wrong in your own `server/lib/csv.js` reasoning earlier — `toCsv` formats whatever it's handed, it doesn't choose.
